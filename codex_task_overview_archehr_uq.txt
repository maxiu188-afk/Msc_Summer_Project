# Task Overview for Codex: Lightweight Uncertainty Quantification for Grounded Clinical QA

## 0. Project Context

This project investigates **lightweight uncertainty quantification (UQ) for grounded clinical question answering**, using **ArchEHR-QA** as the primary target dataset.

The core research idea is:

> Semantic Entropy (SE) is a strong uncertainty baseline for free-form LLM answers, but it is expensive because it requires multiple generations. Semantic Entropy Probes (SEPs) estimate semantic uncertainty from hidden states of a single generation, making them much cheaper. This project adapts SEPs to grounded clinical QA and tests whether token selection can improve their reliability.

The implementation should be modular and incremental. The project should remain useful even if the later SEP/token-selection experiments do not outperform the baseline.

## 2. Main Research Objective

Build an experimental pipeline to evaluate uncertainty estimation methods for grounded clinical QA.

The pipeline should support:

1. Loading ArchEHR-QA-style examples.
2. Generating grounded answers using question + provided clinical evidence.
3. Computing baseline uncertainty scores.
4. Computing Semantic Entropy from multiple generations.
5. Training Semantic Entropy Probes from hidden states.
6. Testing whether different token-selection strategies improve SEP performance.
7. Evaluating uncertainty scores against answer correctness or proxy labels.

### Tasks

1. Implement dataset loading.
2. Implement prompt construction:
   - Input: patient question, optional clinician rewrite, evidence sentences.
   - Output: grounded answer with citations if feasible.
3. Implement answer generation with an open-weight causal LLM.
4. Implement baseline uncertainty methods:

   - Token entropy.
   - Sequence negative log likelihood or normalized log likelihood.

   - Generate multiple answers for the same input.

## 5. Stage 2: Adapt Semantic Entropy Probes to Clinical QA

### Goal

Train probes to approximate Semantic Entropy from hidden states of a single generation.

### Rationale

SE is expensive at test time because it needs multiple generations. SEP uses SE as a training target but only needs one generation at inference time.

### Tasks

1. For each training example:
   - Run greedy generation once.
   - Save hidden states from selected layers and token positions.
   - Run multi-sample generation to compute SE target.
2. Convert raw SE values into labels:
   - Binary high-SE / low-SE label using a threshold.
   - Prefer the regression-tree-style split used in the SEP paper.
   - Optionally also support direct regression to raw SE.
3. Train lightweight probes:
   - Start with logistic regression or ridge regression.
   - Input: hidden state vector.
   - Target: binarized SE label or raw SE.
4. Evaluate SEP:
   - How well SEP predicts high/low SE.
   - How well SEP detects incorrect answers.
   - Compare against SE, token log probability, token entropy, and verbalized confidence.
5. Test generalization:
   - Train on auxiliary QA data if ArchEHR-QA is too small.
   - Validate/test on ArchEHR-QA.
   - Keep dataset splits explicit and reproducible.

### Deliverables

- Hidden-state extraction script.
- SE target generation script.
- SEP training script.
- SEP inference script.
- SEP evaluation report/table.

## 6. Stage 3: Token Selection for SEP

### Goal

Investigate whether choosing better token positions improves SEP performance on longer grounded clinical answers.

### Motivation

The original SEP paper mainly uses fixed token positions such as:

- TBG: token before generation.
- SLT: second-last token / last generated content token.

However, in longer clinical answers, uncertainty-relevant information may be concentrated in only a few tokens. Token selection may therefore improve probe reliability.

### Candidate Token Selection Strategies

Implement simple strategies first:

1. **Fixed-token baselines**
   - TBG.
   - SLT.
   - First generated token.
   - Last generated token.

2. **Token uncertainty selection**
   - Select top-k generated tokens by token entropy.
   - Select top-k generated tokens by low token probability.
   - Aggregate their hidden states by mean or max pooling.

3. **Citation/evidence-aware selection**
   - Select tokens near cited sentence markers if citations are generated.
   - Select tokens overlapping with medical entities or evidence terms if easy to implement.
   - Keep this optional; do not let it block the main experiment.

4. **Multi-token pooling**
   - Mean pooling over all generated tokens.
   - Mean pooling over top-k uncertain tokens.
   - Max pooling over top-k uncertain tokens.
   - Concatenate fixed token representation with pooled top-k representation if dimension is manageable.

### Important Constraint

Do not implement a large complex model unless the simpler probe pipeline is already stable.

Start with lightweight and interpretable methods:

- Logistic regression.
- Ridge regression.
- Small MLP only if necessary.

### Deliverables

- Token-selection module.
- Configurable SEP feature extractor.
- Comparison table:
  - fixed token vs top-k uncertainty tokens vs pooled tokens.
- Analysis of whether token selection helps, hurts, or has no clear effect.

## 9. Model and Compute Notes

The implementation should support small smoke tests first.

Recommended development order:

1. Run with a tiny model or very small subset.
2. Verify data loading and output formats.
3. Verify token probabilities and hidden states are being saved.
4. Verify SE computation on 2-5 examples.
5. Scale up only after the pipeline is stable.

Do not assume GPU is always available. The code should fail gracefully if CUDA is unavailable.

Use `local_files_only` or offline mode if the model has already been downloaded locally.

## 10. Restricted Dataset Rules

Do not automatically download restricted clinical datasets.

For PhysioNet/MIMIC/i2b2-based datasets:

- Assume the user manually downloads the data.
- Never ask for or store usernames, passwords, API keys, or credentials.
- Never hard-code private paths except through config files.
- Implement loaders that read from local paths such as:

```text
data/raw/archehr_qa/
```

Public datasets may have optional download scripts, but this is not the priority.

## 11. Evaluation Target

The central evaluation question is:

> Does an uncertainty score successfully identify model answers that are likely to be incorrect, unsupported, or unreliable?

Possible correctness targets:

1. Exact/semantic match against gold answer.
2. LLM-as-judge correctness evaluation.
3. Citation/evidence support score.
4. Existing ArchEHR relevance/factuality metrics, if available.
5. Human/manual inspection for a small subset.

Keep correctness/evaluation logic modular because this is a known difficulty for ArchEHR-QA.
